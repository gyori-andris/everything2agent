# Roadmap

The roadmap stabilizes the generic textual primitive before exploring runtimes or
domain integrations. A homelab, software repository, or research corpus may serve as
a testing ground; none defines the architecture or becomes a required backend.

## v0.1 — Object identity, open requests, visible limits

Question: can an existing resource be represented as a persistent agent identity
with scoped context?

Deliver a small object-document convention, generic object and supervisor skills,
and a synthetic fixture. Test normal diagnosis, missing observations, and a shared
contract failure. Establish whether progressive disclosure preserves answer quality
and reduces supervisor context. Measure total cost separately.

The repository provides a manual rehearsal. Live multi-session evaluation remains
to be completed, so v0.1 establishes a candidate convention rather than a validated
performance claim.

## v0.2 — Semantic ownership and late-bound work

Question: is semantic ownership sufficient to make an object a general-purpose
agent without compiling its responsibilities?

V0.2 defines an Agent Object as the agent for an entire semantic asset. It accepts
arbitrary work concerning that asset. The descriptor identifies the object and its
meaningful borders; it does not enumerate supported tasks or express permissions.

Deliverables:

- replace persistent responsibility with semantic ownership;
- state explicitly that the convention is not access control or identity provision;
- keep context references distinct from permissions and current evidence;
- accept novel requests against an unchanged descriptor;
- derive work at activation time;
- preserve useful owned work when a request crosses a semantic border;
- return the remaining question to a supervisor rather than ending at `out of scope`;
- treat relationships as navigation hints rather than gates;
- make ambiguous, missing, and overlapping ownership visible;
- define personality as optional representation rather than authority or task scope;
- add personality and no-deadzone conformance checks; and
- retain ordinary request-shaped results rather than imposing one domain schema.

Acceptance cases:

1. One unchanged object handles several materially different requests, including a
   request not anticipated by its document or personality.
2. A change request concerning the owned object is not rejected merely because no
   mutation capability was declared in the object document.
3. Missing runtime facilities are reported as session facts, not semantic bans.
4. A cross-object request produces useful partial work plus a precise delegation
   need; it never disappears into a bare scope refusal.
5. An absent relationship link does not prevent the supervisor from discovering or
   reporting another owner.
6. Overlapping objects can contribute different semantic perspectives without being
   treated as a permission conflict.
7. Removing a personality changes voice or emphasis, not accepted work, ownership,
   evidence discipline, or delegation behavior.
8. The complete primitive remains understandable as text without running code.

## v0.3 — Optional textual modules

Question: can recurring concerns and useful procedures be compiled into reusable
text without narrowing the general primitive?

A module is optional textual context supplied for an activation or recurring concern.
Common forms may include personality, responsibility, and procedure modules, but
the core does not require a rigid module taxonomy.

Deliverables:

- define a minimal, human-readable module convention;
- show how a module is attached without changing object identity or ownership;
- preserve generic reasoning when no module applies;
- distinguish recurring assignment from a reusable method;
- record provenance and human-readable validity conditions;
- allow repeated work to suggest a proposed module;
- keep generated modules inspectable and editable as text;
- provide module conformance checks; and
- treat graph resolvers or validators as replaceable acceleration helpers.

Acceptance cases:

1. Removing every module leaves the Agent Object generally functional.
2. An irrelevant module does not cause a valid novel request to be rejected.
3. A responsibility module can introduce recurring work without redefining ownership.
4. A procedure module can accelerate work without becoming its mandatory method.
5. A personality module cannot alter semantic borders or suppress delegation.
6. A generated module remains a proposal until the surrounding workflow accepts it.
7. No module claims to provision credentials, enforce permissions, or create runtime
   isolation.

## Future concept collection

After v0.3, concepts remain deliberately unversioned until experiments justify a
delivery order:

- object directories and semantic discovery;
- relationship-graph resolution and missing-owner discovery;
- supervisor routing heuristics and delegation traces;
- parallel activation, loop detection, and investigation budgets;
- direct object-to-object delegation;
- dynamic module suggestion, evaluation, expiration, and supersession;
- object lifecycle and identity across moves or recreation;
- human annotation and revision of object representations;
- automatic suggestions for missing context or relationships;
- context retrieval, compression, and session continuity;
- evidence freshness, disagreement, and provenance handling;
- A2A publication and MCP-backed context;
- runtime integrations such as Hermes;
- external identity, credential, and security systems;
- experiments using infrastructure, SWE, and research objects;
- comparison with monolithic agents; and
- correctness, cost, latency, scope, and delegation-quality evaluation.

These are research directions, not promised milestones. Domain-specific adapters,
deployment automation, or identity provisioning belong in integrations or testing
environments unless repeated evidence shows that the generic primitive requires a
new textual concept.
